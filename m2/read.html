1. Performance and Amdahl's law

Lecture 14 (part 2), textbook 2.6.1–2.6.2

Speedup grows as you add cores, but each extra core is worth less than the one before, and the serial part of the program sets a hard ceiling.

Speedup and efficiency

S = Tserial / Tparallel     E = S / p = Tserial / (p × Tparallel)
  • Linear speedup is the best case: S = p, so Tparallel = Tserial / p and E = 1. It normally doesn't happen.
  • Speedup depends less on input size than run time does, so it's the easier number to talk about.
  • Efficiency is the share of the work each core contributes, its utilization. As p grows, S usually rises while E falls.

The lecture's example: speedup keeps increasing, but efficiency drops, so each added processor is worth less.

Overhead

Tparallel = Tserial / p + Toverhead

Overheads that grow with the number of threads or processes: managing threads, critical sections, mutex function calls, network I/O (distributed systems) and file I/O. They're why efficiency usually drops as p grows. When the problem gets bigger, overhead usually grows more slowly than Tserial, so speedup and efficiency both go up.

Amdahl's law

Let a be the inherently serial fraction of the program, so 1 − a is parallelizable and gets perfect speedup on p cores:

S = 1 / ( (1 − a)/p + a )   →   1/a as p → ∞
  • Lecture example: Tserial = 20 s, 90% parallelizable. Tparallel = 18/p + 2 s, so S = 1 / (0.9/p + 0.1).
  • Limits: a = 0.5 → max 2; a = 0.1 → max 10; a = 0.05 → max 20; a = 0.01 → max 100.
  • Use it to bound the payoff: measure the serial portion, compute the ceiling, then decide how many cores (or how much cloud hardware) is worth buying.
  • Amdahl's law says parallelization alone never gives super-linear speedup. With a = 0, S = p.

2. Parallel architectures and data layout

Lecture 14 (part 1) and Lecture 7, textbook 2.3

Flynn's taxonomy classifies machines by instruction and data streams; how you lay out data in memory decides how fast any of them can feed on it.

Flynn's taxonomy

ClassMeaningExample
SISDSingle instruction, single dataClassic serial von Neumann single core
SIMDOne control unit, many ALUs: the same instruction on many data items at once (m ALUs → arithmetic up to m× faster)Vector processors, x86 SSE; good for simple loops over big arrays (data parallelism), not much else
MISDMultiple instructions on a single data streamVery few real systems
MIMDIndependent cores, each with its own control and ALU, running asynchronouslyMulticore CPUs (shared memory) and clusters (distributed memory)

Vector processors (SIMD)

Operate on whole vectors (arrays) in vector registers; the same operation is applied to every element at once. Vector length is fixed per system, normally 4 to 256 elements of 64 bits.

BenefitsDrawbacks
Fast and easy to use; compilers are good at finding code to vectorize and give feedback on loops they couldn't; high memory bandwidth; every loaded item is used (unlike a cache line) Don't work well with irregular data structures (anything but arrays); hard to scale, because longer vectors aren't very useful

Shared vs distributed memory

  • UMA (uniform memory access): one big memory, same access time for every core. Easier to program.
  • NUMA (nonuniform): each chip has its own memory; local access is faster, another chip's memory is slower. Allows more total memory.
  • Cluster: a collection of systems on a commodity network (Ethernet). Nodes are usually shared-memory machines themselves, so clusters are hybrid systems.
  • Grid: many clusters spread over a large geographic area; often heterogeneous (different hardware and operating systems).
  • Interconnects: a bus is cheap and flexible but shared, so more processors means more waiting. A crossbar switch gives multiple paths so processors can reach different memory modules at once; it's faster but expensive, and the only conflict is two processors wanting the same module.

Data layout: flat and contiguous

  • Store 2D data as one 1D array, a[i*N + j], rather than an array of row pointers or a linked structure. Looping over a flat array touches neighbouring addresses: good spatial locality, so each cache line fetched is fully used.
  • Pointer-chasing structures (lists, trees, arrays of pointers to separately allocated rows) scatter data across memory and waste cache lines.
  • A contiguous block can be moved in one piece: one MPI message (buffer pointer + count) or one copy to the GPU. Scattered data needs many messages or a packing step first.

3. Distributed memory and MPI basics

Lecture 9, textbook 3.1

MPI runs separate processes that share nothing; all data moves in explicit messages, and a receive only completes when communicator, source and tag all match.

Why distributed memory

  • Machines are connected by a network instead of a bus, so sharing data takes time. Threads share data almost instantly.
  • It only pays off when each machine spends more time computing than communicating, so it suits long, data-parallel computations. Example: a render farm sends each machine the scene data for a frame (or a batch of frames).
  • Processes can be on different machines, the same machine, or both; MPI hides which.

MemorySharedDistributed

The hello-world skeleton

#include <mpi.h>
int main(void) {
    char greeting[MAX_STRING];
    int comm_sz, my_rank;

    MPI_Init(NULL, NULL);                       /* start MPI */
    MPI_Comm_size(MPI_COMM_WORLD, &comm_sz);    /* number of processes */
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);    /* my ID, 0 … comm_sz-1 */

    if (my_rank != 0) {                         /* producers */
        sprintf(greeting, "Greetings from process %d of %d!", my_rank, comm_sz);
        MPI_Send(greeting, strlen(greeting)+1, MPI_CHAR, 0, 0, MPI_COMM_WORLD);
    } else {                                    /* rank 0 consumes */
        printf("Process %d of %d is ready to receive\n\n", my_rank, comm_sz);
        for (int q = 1; q < comm_sz; q++) {
            MPI_Recv(greeting, MAX_STRING, MPI_CHAR, q, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
            printf("%s\n", greeting);
        }
    }
    MPI_Finalize();                             /* free MPI's resources */
    return 0;
}
  • Compile with the wrapper mpicc mpi_hello.c -o mpi_hello; run with mpiexec -n 4 ./mpi_hello (4 processes).
  • One program, different behaviour by rank, like fork(). Write it to work for any number of processes.
  • The number of sends and receives must match, or something blocks forever.
  • Because rank 0 receives in rank order (source q), the greetings print 1, 2, 3 every time.

Send and receive

int MPI_Send(const void* buf, int count, MPI_Datatype type,
             int dest, int tag, MPI_Comm comm);
int MPI_Recv(void* buf, int count, MPI_Datatype type,
             int source, int tag, MPI_Comm comm, MPI_Status* status);
  • count is a number of elements, not bytes; type is a macro such as MPI_CHAR, MPI_INT, MPI_DOUBLE. For a string send strlen(s)+1 to include the terminator.
  • In MPI_Recv, count is the buffer capacity; the message can be shorter. It is received successfully if the types match and the buffer is at least as big as the message.
  • A tag is a non-negative int used to tell message types apart (for example, work vs results, as in A2).
  • A communicator is a group of processes that can talk to each other, like a radio channel. MPI_COMM_WORLD holds everyone. Separate communicators keep libraries' messages from being received by accident.
  • Both return MPI_SUCCESS on success, otherwise an error code.

Message matching

A message sent by rank q is received by rank r's MPI_Recv only if all of these agree:

  • the communicators are the same,
  • the tags are the same (or the receiver uses MPI_ANY_TAG),
  • the send's dest is r, and the receive's source is q (or MPI_ANY_SOURCE).

Only the receiver can use wildcards; a sender always names a rank and a tag. There is no wildcard for the communicator.

After a wildcard receive: the status

MPI_Status status;
int n;
MPI_Recv(buf, 256, MPI_CHAR, MPI_ANY_SOURCE, TAG_RESULT, MPI_COMM_WORLD, &status);
int who = status.MPI_SOURCE;            /* which rank sent it */
int tag = status.MPI_TAG;               /* which tag it had   */
MPI_Get_count(&status, MPI_CHAR, &n);  /* how many elements arrived */

MPI_Status has at least MPI_SOURCE, MPI_TAG and MPI_ERROR. The count isn't a field: call MPI_Get_count with the type. MPI_Recv's return value is only an error code, and sizeof(buf) is the buffer size, not the message size. Pass MPI_STATUS_IGNORE if you don't need any of this.

MPI_ANY_SOURCE lets a manager take results in whatever order workers finish, instead of waiting on rank 1 while rank 7 is already done.

Ordering and blocking

  • Nonovertaking: two messages from the same sender to the same receiver (that both match) arrive in the order sent.
  • There is no global order across different senders.
  • MPI_Recv always blocks until a matching message arrives.
  • MPI_Send may buffer the message and return, or block until it's received; which one is implementation-dependent. After a buffered send you don't know whether it was delivered.
  • Non-blocking MPI_Isend/MPI_Irecv exist; we don't use them in this course.

Blocking pitfalls: a receive with no matching send hangs forever. If the source, tag or communicator doesn't match, the receive never completes (or it matches the wrong send). A send that blocks waiting for a receive can hang. A buffered send with no receive is lost.

Input and output

  • Assume only rank 0 reads stdin. It must send (or broadcast) what it reads to the others.
  • Most implementations let every rank write to stdout and stderr, but the order is nondeterministic: lines can appear in any order or interleave. For ordered output, send everything to rank 0 and print there.
void Get_input(int my_rank, int comm_sz, double* a_p, double* b_p, int* n_p) {
    if (my_rank == 0) {
        scanf("%lf %lf %d", a_p, b_p, n_p);
        for (int dest = 1; dest < comm_sz; dest++) {
            MPI_Send(a_p, 1, MPI_DOUBLE, dest, 0, MPI_COMM_WORLD);
            MPI_Send(b_p, 1, MPI_DOUBLE, dest, 0, MPI_COMM_WORLD);
            MPI_Send(n_p, 1, MPI_INT,    dest, 0, MPI_COMM_WORLD);
        }
    } else {
        MPI_Recv(a_p, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        MPI_Recv(b_p, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        MPI_Recv(n_p, 1, MPI_INT,    0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
    }
}

All three messages use tag 0, and that's safe: nonovertaking guarantees a, b, n arrive in the order rank 0 sent them.

4. Collectives and the trapezoidal rule

Lectures 10 and 11, textbook 3.2–3.4

A collective involves every process in a communicator; MPI does the tree-structured work for you and puts the result where the call says.

Point-to-point vs collective

  • Point-to-point (MPI_Send/MPI_Recv) is between two processes.
  • A collective involves all processes in the communicator, and every one of them must call it. If one rank skips it, the others hang.
  • Collectives take no tag; they're matched by communicator and the order in which they're called.
  • MPI implementations spread the work over a tree (log₂ p rounds) instead of having one process do p − 1 steps, and tune it for the system.
CallPatternWho has the result
MPI_Bcast(data, count, type, root, comm)1 → N, same data to everyoneAll ranks. The root sends; every other rank receives into data
MPI_Reduce(in, out, count, type, op, dest, comm)N → 1, combined with opOnly dest; out isn't set on other ranks
MPI_Allreduce(in, out, count, type, op, comm)N → N ("butterfly")All ranks. Same as Reduce but no dest argument
MPI_Scatter(send, scount, stype, recv, rcount, rtype, src, comm)1 → N, a different chunk to eachEach rank, including src, gets its own chunk in recv; send only matters on src
MPI_Gather(send, scount, stype, recv, rcount, rtype, dest, comm)N → 1, chunks assembled in rank orderOnly dest's recv is filled

Operators: MPI_SUM, MPI_PROD, MPI_MIN, MPI_MAX and others. With count > 1 the operation is applied element by element to arrays. Example: MPI_Reduce(&tmpVal, &sum, 1, MPI_DOUBLE, MPI_SUM, 0, comm) adds one double from each process into sum on rank 0.

The typical pattern

  1. Rank 0 reads the parameters; broadcast them once.
  2. Every rank computes locally on its own block.
  3. Combine with one Reduce (answer on rank 0) or Allreduce (everyone needs it).

Don't reduce after every element, and don't send each element to a worker and back: on a slow network every message is expensive. The classic send/gather pattern from the hello example (workers send, rank 0 receives in a loop) does the same job as a gather or reduce, just serially.

Trapezoidal rule

Approximate the area under f from a to b with n trapezoids of width h:

h = (b − a)/n    area ≈ h [ f(x0)/2 + f(x1) + … + f(xn−1) + f(xn)/2 ]

One trapezoid has area (h/2)(f(xi) + f(xi+1)). It underestimates where f is concave and overestimates where f is convex; narrower trapezoids average the errors out.

double Trap(double left, double right, int count, double h) {
    double estimate = (f(left) + f(right)) / 2.0;
    for (int i = 1; i <= count - 1; i++)
        estimate += f(left + i*h);
    return estimate * h;
}

Foster's steps for MPI: each process gets its own sub-interval and computes a partial integral; every process needs a, b and n; partial results are summed on one process. Process 0 also does the I/O.

Get_input(my_rank, comm_sz, &a, &b, &n);
h = (b - a) / n;                       /* same on every process */
local_n = n / comm_sz;                 /* assumes comm_sz divides n */
local_a = a + my_rank * local_n * h;
local_b = local_a + local_n * h;
local_int = Trap(local_a, local_b, local_n, h);

MPI_Reduce(&local_int, &total_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);

The first version ended with rank 0 receiving comm_sz − 1 messages in a loop and adding them; the improved version replaces that with MPI_Reduce, and replaces the send loop in Get_input with three MPI_Bcast calls (rank 0 does the scanf inside if (my_rank == 0), but every rank calls MPI_Bcast). Example: a = 0, b = 8, n = 1024, 4 processes → h = 1/128, local_n = 256, rank 2 integrates from 4 to 6.

5. GPGPU concepts

Lecture 15

A GPU is thousands of simple cores running one kernel over a stream of data; it lives in its own memory, so the data has to be copied there and back.

Why GPUs exist

  • A 1920 × 1080 frame is about 2 million pixels; at 60 FPS that's about 120 million pixel colours per second, each needing several matrix/vector operations. A CPU can't keep up.
  • GPUs skip complex branch logic and cache management and spend their transistors on processing units: a few hundred to over 10,000 cores, against 2–96 (up to about 250) for CPUs.
  • GPGPU: general-purpose computing on the GPU. Physics simulation, machine learning (it largely enabled the last 15–20 years of ML), robotics, image/audio/video processing, science, finance.

The stream programming model

  • A stream is an ordered set of data of one type (numbers, points, triangles, matrices), usually thousands of elements or more.
  • A kernel is a small program applied to whole streams, taking one or more streams in and producing one or more out. The most common use is a map: one function on every element. Others: expansion (more outputs than inputs), reduction (combine elements), filter (output a subset).
  • Kernel outputs depend only on kernel inputs. A thread can read any input element but writes its own output, and must not depend on another thread's output. That independence is what lets a serial-looking kernel run data-parallel.
  • Only one kernel is applied to a stream at a time; several kernels run in sequence.

SIMD vs SIMT

  • SIMD (CPU vector units): one thread, one register file with very wide registers; the same instruction across execution lanes.
  • SIMT (GPU): many threads in lockstep sharing one fetch/decode (one PC), each with its own registers.
  • Threads are grouped into shading units (CUDA cores, SIMT units), which are grouped into compute units of dozens (up to 128 or more) shading units.
  • Divergence: if threads in a lockstep group take different branches, the group runs both paths with inactive lanes masked off, so it costs the sum of both. Anything that breaks uniformity hurts; give every thread the same amount of work.

Heterogeneous computing and the copy cost

  • Pthreads and MPI are homogeneous: every execution unit is a compatible CPU core (Intel and AMD mix fine; Intel and ARM don't).
  • GPGPU is heterogeneous: the host program on the CPU loads the data, sends it and the compiled kernels to the GPU (the device), launches the kernels, then copies the results back.
  • CPU and GPU usually have separate memories, so it borrows from distributed memory: data crosses the bus, and that copy is expensive. For small problems it can be the dominant cost, which is why a naive GPU port can be slower than the CPU version. Once data is on the GPU, kernels access it directly (and can race).
  • Design for it: flat, contiguous buffers, uniform work per thread, minimize CPU–GPU transfers, and give each element enough work to pay for the copy.

Libraries: CUDA (Nvidia's proprietary platform, Nvidia hardware only, most popular), OpenCL (open standard, many platforms, declining) and Nvidia Warp (free, open source, used in this course).

6. Programming with Warp

Lectures 15 and 18

Write the kernel and the host code in Python; Warp compiles the kernel at run time and launches one thread per element of the launch grid.

What Warp does

  • Runs on Nvidia GPUs in parallel (device="cuda"), or on the CPU as a single-threaded serial program (device="cpu") with identical code and semantics. We use "cpu" in the course Docker container (Warp 1.16) and "cuda" on an Nvidia GPU or Google Colab.
  • Both host and kernel code are Python; Warp JIT-generates C++/CUDA and compiles it. In CUDA or OpenCL you'd write host code in C and kernels in a separate language.
  • Warp initializes itself on first use; wp.init() in older examples still works but isn't required.

Example: Z = X + Y

import numpy as np
import warp as wp

@wp.kernel
def addArrays(x: wp.array(dtype=float),
              y: wp.array(dtype=float),
              z: wp.array(dtype=float)):
    tid = wp.tid()              # this thread's index
    z[tid] = x[tid] + y[tid]    # one element per thread

device = "cpu"
hostX = np.array([1, 2, 3, 4], dtype=np.float32)
hostY = np.array([2, 3, 4, 5], dtype=np.float32)
x = wp.array(hostX, dtype=float, device=device)   # copy host → device
y = wp.array(hostY, dtype=float, device=device)
z = wp.zeros(len(hostX), dtype=float, device=device)

wp.launch(kernel=addArrays, dim=len(z), inputs=[x, y], outputs=[z], device=device)
print(z.numpy())                                   # copy device → host
  • @wp.kernel marks the kernel. Warp is statically typed: every argument needs a type annotation, and Warp compiles from them.
  • Kernels don't return values; they write results into an output array argument.
  • You write the body for one element; conceptually the kernel applies to the whole stream.
  • wp.tid(): a scalar for a 1D launch (i = wp.tid()), a tuple for 2D/3D (i, j = wp.tid(), i, j, k = wp.tid()).

wp.launch

wp.launch(kernel, dim=N, inputs=[...], outputs=[...], device="cuda")
  • dim is the launch grid (how many threads), not an array's shape. For a simple map they coincide because we choose dim=len(array) or dim=array.shape.
  • Warp concatenates inputs= and outputs= into the kernel's positional arguments, in order. It does not check which arrays you write to; outputs= is documentation.
  • device is optional and defaults to Warp's default device.

Passing constants

Pass values like k, a filter radius or sigma as ordinary typed kernel arguments:

@wp.kernel
def scaleArray(source: wp.array(dtype=wp.float32),
               dest: wp.array(dtype=wp.float32),
               factor: float):
    i = wp.tid()
    dest[i] = factor * source[i]

wp.launch(scaleArray, dim=source.shape, inputs=[source, dest, 2.0], device=device)

The value is read at launch, so you can change it without recompiling. (Closures are for values needed at compile time; not used in this course.)

The image pipeline

  1. Load: image = Image.open(fileName) (PIL/Pillow).
  2. Check the mode: image.mode.
  3. To NumPy: npInData = np.asarray(image, dtype=np.float32).
  4. To Warp: inWarpImage = wp.array(npInData, dtype=wp.float32, device=device).
  5. Output: outWarpImage = wp.zeros_like(inWarpImage) (same shape, dtype, device, all zero).
  6. Launch the kernel.
  7. Back to NumPy: npOutData = outWarpImage.numpy().
  8. To PIL: Image.fromarray(np.uint8(np.clip(np.rint(npOutData), 0, 255))).
  9. Save: imageOut.save(outFileName).

Why clip: sharpening overshoots above 255 and below 0 at strong edges, and np.uint8 wraps around instead of clamping, which shows up as salt-and-pepper along edges.

A filter kernel

@wp.kernel
def blurGreyscale(inputImage: wp.array2d(dtype=wp.float32),
                  outputImage: wp.array2d(dtype=wp.float32)):
    i, j = wp.tid()
    height = inputImage.shape[0]
    width = inputImage.shape[1]
    # border policy for the slide: copy edge pixels (A3 doesn't allow this)
    if i == 0 or j == 0 or i == height - 1 or j == width - 1:
        outputImage[i, j] = inputImage[i, j]
        return
    acc = 0.2 * inputImage[i, j]
    acc += 0.2 * inputImage[i - 1, j]
    acc += 0.2 * inputImage[i + 1, j]
    acc += 0.2 * inputImage[i, j - 1]
    acc += 0.2 * inputImage[i, j + 1]
    outputImage[i, j] = acc

Each thread writes exactly one output cell and only reads the input, so it's race-free with no synchronization. Never filter in place: neighbours would read values that are already filtered.

Timing on a GPU

  • CUDA launches are asynchronous: wp.launch returns before the work is done, so a timer around it measures only the launch.
  • .numpy() blocks until the kernel finishes, then copies; a timer ending there hides the kernel time inside "download".
  • The first launch of a module compiles it (seconds); run once before timing.
  • Use wp.ScopedTimer(name, synchronize=True), time upload, kernel and download separately, and report the median of several runs.

7. Image processing

Lectures 16 and 17

Most filters are a convolution: each output pixel is a weighted sum of its input neighbourhood. Smoothing kernels sum to 1, sharpening kernels sum to 0, and the border needs a policy.

Images and neighbourhoods

  • A greyscale image is one matrix of intensities; a colour image is three (R, G, B) or four (RGBA). Simple algorithms treat each colour channel as its own greyscale image.
  • 4-neighbours of (x, y): (x±1, y) and (x, y±1). Add the four diagonals for the 8-neighbours.
  • Filtering (image restoration or enhancement): removing noise, sharpening, contrast enhancement.

Discrete convolution

g(x, y) = Σi=−1..1 Σj=−1..1 w(i, j) · f(x + i, y + j)
  1. Centre the kernel on pixel P (so it needs odd dimensions: 3 × 3, 5 × 5, …).
  2. Multiply each pixel in the k × k neighbourhood by the kernel coefficient over it.
  3. Sum the products.
  4. Write the (normalized) sum to P's position in the output image.
  • A kernel is also called a mask or a filter. Uniform: every coefficient the same; nonuniform: different weights; omnidirectional: same response in every direction.
  • Normalization: divide by the sum of the coefficients, usually written outside the matrix (1/9, 1/25). Then a constant area stays the same and the filter adds no bias: the mean intensity is preserved. If you forget, a 3 × 3 box filter makes the image about 9× brighter, and most of it clips to 255.
  • Shapes: rectangular 5 × 5 (1/25), circular pill-box (1/21, corners zero), pyramidal (1/81, weights 1-2-3-2-1 outer products), cone, Gaussian.

Worked example from the lecture (3 × 3 mean): neighbours 131, 134, 193, 251, 249, 221, 220, 206, 230 sum to 1835; ÷ 9 ≈ 204.

Border strategies

Convolution needs the whole kernel inside the image. A 3 × 3 kernel can process only the (M − 2) × (N − 2) interior; in general a kernel with half-size (m₂, n₂) processes (M − 2m₂) × (N − 2n₂), so 5 × 5 → (M − 4) × (N − 4), 7 × 7 → (M − 6) × (N − 6).

Low-pass, high-pass, sharpening

  • Low-pass filter (LPF): smoothing / de-noising. It passes low spatial frequencies and removes large, sudden, closely spaced intensity changes, whether they're noise or fine detail.
  • High-pass filter (HPF): image minus its low-pass version; keeps sudden changes such as object boundaries. An omnidirectional HPF kernel is positive at the centre and negative around it, and its coefficients sum to zero: 
    −1 −1 −1
−1  8 −1
−1 −1 −1
    In a constant or slowly changing area it gives zero or near zero; at a rapid change it gives a large value. Sharpening also amplifies noise, so de-noise first.
  • High-boost filter: part of the high-pass added back to the image.

Unsharp masking

g = f − S(f)      fUM = f + k · g
  • S(f) is a blurred version of f, so g is the edge image: the original minus its blur.
  • k controls sharpening strength; reasonable values are 0.2 to 0.7. With k > 1 it's called a high-boost filter.
  • It's multi-step: blur, subtract, scale, add.
  • Limitations: noise sensitivity (it emphasizes high frequencies) and overshoot at sharp edges: the edge gets steeper by getting taller, so values go past 0 and 255 and must be clipped.
  • History: Schreiber (1970), for newspaper wirephotos, based on photographic masking.

Smoothing filters

  • Mean (box, sliding mean) filter: replace each pixel by the average of its neighbourhood. Reduces noise (effective against Gaussian noise) but blurs edges, because edges are sharp transitions too. Bigger kernels or repeated passes blur more. It's the opposite of sharpening.
  • Gaussian filter: nonuniform weights w(i, j) = e−(i² + j²)/(2σ²) for i, j from −⌊3σ⌋ to ⌊3σ⌋ (weights beyond 3σ are negligible). More weight in the centre; larger σ means a wider kernel and more blurring; rotationally symmetric (isotropic), so no directional bias. σ² = 1 gives a 7 × 7 kernel with centre 159/1000.
  • Median filter (a rank or order-statistic filter, non-linear): sort the neighbourhood and take the middle value. Removes impulse (salt-and-pepper) noise when noisy pixels are less than half the neighbourhood. It doesn't compress the brightness range, so it keeps edges sharp, including straight edges. But it's non-specific: any structure smaller than half the neighbourhood (a thin line, a small object) is removed too. Repeated passes cause posterization.

Lecture example: the 25 values in a 5 × 5 neighbourhood sorted ascending; the 13th (middle) is 98, so the pixel becomes 98.

Implementation habits

  • Store 2D images as 1D, contiguous arrays (or one Warp array), never as arrays of separate rows.
  • Read from the input, write to a separate output; avoid unnecessary copies, especially between host and device.

Pitfalls the exam can test

  • Choosing one message per element over a slow network, or an Allreduce inside the inner loop.
  • Expecting MPI_Recv to return the count, or status.MPI_TAG to hold the sender.
  • Calling a collective on only some ranks; expecting Reduce's result on every rank.
  • Assuming messages from different senders arrive in rank order.
  • Thinking device="cpu" runs in parallel.
  • Returning a value from a Warp kernel, or leaving out type annotations.
  • Forgetting to normalize a smoothing kernel; filtering the alpha channel; saving without clipping.
  • Porting a tiny or low-work-per-byte problem to the GPU and expecting a speedup.
