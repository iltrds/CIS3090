1. Why parallel computing

Lecture 1, textbook Ch. 1

Single-core speed stopped growing fast, so performance now comes from more cores, and serial programs don't use extra cores automatically.

Concurrent, parallel, distributed

TermMeaningNeeds multiple cores?Example
ConcurrentMultiple tasks in progress at once; time-slicing is enoughNoGUI with input, UI and worker threads; any modern OS
ParallelTasks cooperate closely and execute simultaneously to solve one problemYespigz, FFmpeg, parallel sum
DistributedProgram cooperates with other programs, often over the Internet; loosely coupledYes (separate machines)Web apps with a database backend, email, multiplayer games

Parallel and distributed programs are also concurrent. The OS handles concurrency (scheduling 400 threads on 16 cores); it does not parallelize a compiled serial binary. Auto-parallelization tools like OpenMP only work in narrow cases.

Why hardware went multicore

  • CPU performance grew about 50% per year from 1986 to 2002, then about 20% per year. Ten years at 50% is 1.5¹⁰ ≈ 58× (the lecture's "60×"); at 20% it's 1.2¹⁰ ≈ 6×. The textbook quotes under 4% per year for 2015–2017.
  • Smaller transistors are faster, but faster means more power, and power becomes heat. Air-cooled chips hit their heat limit. Quantum effects and switching delays also cap clock speed.
  • The fix: put more complete cores on one chip instead of making one core faster.
  • Moore's law (Gordon Moore, 1965): transistor count doubles about every two years (originally every year). An observation, not a physical law. More transistors means more cores.
  • A GPU has many small, simple cores tuned for vector and small-matrix math (1,024–4,096 is typical). GPGPU is using them for general computation.

Why we write parallel programs

Running several copies of a serial program (one per folder of images) is easy parallelism, but usually we want one program to finish faster. Translation programs can recognize simple constructs like a sum loop and swap in a pre-written parallel version, but the best parallel algorithm is often completely different from the serial one, like the tree-structured global sum.

Task vs data parallelism

  • Data parallelism: split the data; everyone does the same thing on their share. Each TA grades a pile of whole exams. Usually easier, so start here.
  • Task parallelism: split the operations; each worker does something different. Each TA grades one question on every exam.
  • In the global sum, computing partial sums is data-parallel; the master receiving and adding while others send is task-parallel.

Coordinating cores needs communication (sending data), load balancing (equal work so nobody idles) and synchronization (cores run at their own pace, so some must wait, e.g. until the master has read the input).

Real examples from lecture

  • Pthreads: pigz, pbzip2, FFmpeg. MPI: LAMMPS, GROMACS, OpenFOAM. GPGPU (Warp): AI, simulation, image processing.
  • pigz on a 10-core M1 Max, 1 GB file: 34.7 s serial vs 4.7 s on 10 cores, a speedup of about 7.4. The parallel run's user time (39 s) is higher than serial: total CPU work went up from overhead while wall time went down.

2. Designing parallel programs

Lecture 2, textbook Ch. 1.3–1.4 and 2.7–2.9

The whole course reuses one pattern: split n items evenly over p workers, compute in parallel, then combine the results with a reduction.

Dividing n items among p workers

The lecture's split, used in every code example: everyone gets ⌊n/p⌋ and the first n mod p workers get one extra.

int q = n / p, r = n % p;
int my_count = q + (rank < r ? 1 : 0);
int my_first = rank * q + (rank < r ? rank : r);   /* my_last = my_first + my_count (exclusive) */
  • Largest share ⌈n/p⌉, smallest ⌊n/p⌋, difference at most 1. Shares always sum to n.
  • The alternative (⌈n/p⌉ to the first p−1 workers, the rest to the last) can leave the last worker far less: 217 exams over 6 TAs gives 37×5 + 32. Both finish in 37 "steps" if you must wait for everyone; the even split wins when finished workers can move on.

Reductions

A reduction repeatedly applies a binary operator (+, ×, max) to a sequence to get one value, kept in a reduction variable.

Combine methodSteps on core 08 cores1000 cores
Serial: core 0 receives and adds p − 1 valuesO(p): p − 17999
Tree: pairs, then pairs of pairsO(log p): ⌈log₂ p⌉310

Both do p − 1 additions in total; the tree overlaps them. Pattern for 8 cores: round 1, 0←1, 2←3, 4←5, 6←7; round 2, 0←2, 4←6; round 3, 0←4. Partner = rank XOR 2ᵏ (textbook Exercise 1.4).

Total parallel-sum time is O(n/p) + O(log p). The log p term only matters when each core's work is tiny (n barely bigger than p). This analysis assumes communication is nearly free; if sending costs more than adding, the tree can be no faster, or even slower. Always check your cost assumptions, like comparisons vs swaps in sorting.

Data vs task parallelism

Embarrassingly parallel: subtasks need little or no communication (filters on a folder of photos). Hard to parallelize: recurrences like A[i] = F(A[i-1]), because you can't get A[k] without computing everything before it.

Definitions

  • Communication: one core sends data to another.
  • Load balancing: keeping as many cores busy as possible.
  • Synchronization: controlling when cores start a task or access data. Cores are not automatically in step.
  • Shared memory: every core reads and writes one memory over a bus (Pthreads, OpenMP). Distributed memory: each core has private memory and sends messages over a network (MPI).

Foster's methodology

  1. Partitioning: divide computation and data into the smallest tasks; identify what can run in parallel and what is inherently serial.
  2. Communication: what data must move between those tasks? Start from what each task needs to know.
  3. Agglomeration (aggregation): combine fine tasks into bigger ones (if A must precede B, merge them) to cut the task count and communication.
  4. Mapping: assign the composite tasks to threads or processes so work is balanced and communication is minimal.

Ch. 2.8–2.9 assumptions: SPMD programs (one executable that branches on rank), homogeneous MIMD, at most one thread per core, static threads (started near the beginning, joined near the end). Compile with gcc -g -Wall -o prog prog.c; add -O2 when timing.

3. Pthreads basics

Lectures 3 and 4, textbook Ch. 4.1–4.3

A Pthreads program is an ordinary C program that starts threads with pthread_create and waits for them with pthread_join. Globals are shared; locals are private.

Threads vs processes

ThreadsProcesses
MemoryShare data, code, heap and file descriptors; own stack and program counterSeparate address spaces
CostCheap to create and switchMore memory; slower to spawn and switch
CommunicationShared variables (fast)Pipes, signals, explicit shared memory
FailureOne thread's crash kills the whole processIsolated from each other
CorrectnessShared data is a major source of bugsForces cleaner habits; privilege separation

Process primitive → thread primitive: fork → pthread_create, exit → pthread_exit, waitpid → pthread_join, atexit → pthread_cleanup_push, getpid → pthread_self, abort → pthread_cancel.

The API you must be able to read

#include <pthread.h>      /* compile: gcc -O2 -std=c99 -pthread prog.c  (or -lpthread) */

void* worker(void* arg);  /* REQUIRED signature: one void* in, one void* out */

int pthread_create(pthread_t* tid,             /* out: opaque handle          */
                   const pthread_attr_t* attr,  /* NULL = default attributes   */
                   void* (*fn)(void*),          /* the thread function         */
                   void* arg);                  /* passed to fn; returns 0 = OK */
int pthread_join(pthread_t tid, void** retval); /* blocks until tid ends       */

The textbook's hello-world (Program 4.1), condensed:

int thread_count;                          /* global = shared */

void* Hello(void* rank) {
    long my_rank = (long) rank;            /* local = private: each thread has its own stack */
    printf("Hello from thread %ld of %d\n", my_rank, thread_count);
    return NULL;
}

int main(int argc, char* argv[]) {
    thread_count = strtol(argv[1], NULL, 10);
    pthread_t* handles = malloc(thread_count * sizeof(pthread_t));
    for (long t = 0; t < thread_count; t++)
        pthread_create(&handles[t], NULL, Hello, (void*) t);  /* long, not int, on 64-bit */
    printf("Hello from the main thread\n");
    for (long t = 0; t < thread_count; t++)
        pthread_join(handles[t], NULL);
    free(handles);
    return 0;
}

Passing several values: allocate one struct per thread (rank, start, count, pointers) and pass its address. Never pass &t of the loop variable: every thread reads the same, changing variable.

typedef struct { int start, count; const double* a; double partial; } Args;

void* Sum(void* p) {
    Args* arg = p;
    double s = 0;                                   /* private accumulator */
    for (int i = arg->start; i < arg->start + arg->count; i++) s += arg->a[i];
    arg->partial = s;                               /* own slot: no lock needed */
    return NULL;
}

Behaviour you must know

  • The order in which threads run and print is nondeterministic. The OS, not you, places threads on cores.
  • Returning from main ends the process and kills every thread (the lecture's sleep(1) vs sleep(4) demo).
  • Threads are joinable by default. A joinable thread that is never joined leaks memory.
  • Detached threads clean up after themselves and cannot be joined. Use them when nobody needs the result:
pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_create(&tid, &attr, fn, NULL);
pthread_attr_destroy(&attr);
  • Static threads (start all, run to completion) are what we use. Dynamic threads fork a worker per request.

Lecture 3 timings

  • Parallel sum, 160 million elements: 1 thread ≈ 1.5 s, 2 ≈ 0.85 s, 4 ≈ 0.7 s. Small gain because summing is cheap and memory-bound.
  • Naive parallel sort (qsort per section, then a serial merge on main): 1 thread ≈ 27 s, 4 threads ≈ 9 s. The serial merge is the bottleneck.
  • Don't time the random initialization, and fix the seed so runs are comparable.

POSIX feature-test macro (Lecture 4)

POSIX is IEEE's Portable Operating System Interface. macOS and AIX are certified; Linux and Android are "mostly compliant". To compile standard C against POSIX.1-2008 in the Docker Linux image (needed for functions like kill()):

#define _POSIX_C_SOURCE 200809L   /* first line of the file */

or gcc -D_POSIX_C_SOURCE=200809L file.c. It hides implementation-defined extensions so only that POSIX version is visible.

4. Barriers and odd-even sort

Lecture 3

Odd-even transposition sort parallelizes because each phase's compare-swaps touch disjoint pairs. A barrier keeps every thread in the same phase.

Barrier vs join

  • pthread_join waits for one thread, once, until it ends.
  • A barrier holds many threads, repeatedly, at a point in ongoing execution. Nobody passes until everyone arrives; the last arrival releases them all.
pthread_barrier_t barrier;
pthread_barrier_init(&barrier, NULL, count);   /* count = threads required */
int rc = pthread_barrier_wait(&barrier);       /* every participant calls this */
/* exactly one arbitrary thread gets PTHREAD_BARRIER_SERIAL_THREAD; the rest get 0 */
pthread_barrier_destroy(&barrier);

It resets automatically after each release, so reuse it every round. Barriers are an optional POSIX feature (the textbook builds its own); the course's Docker image has them.

Serial odd-even transposition sort

  • Even phase: compare-swap (a[0],a[1]), (a[2],a[3]), …
  • Odd phase: compare-swap (a[1],a[2]), (a[3],a[4]), …
  • n elements need at most n phases. Trace: 5 9 4 3 → even: 5 9 3 4 → odd: 5 3 9 4 → even: 3 5 4 9 → odd: 3 4 5 9.
  • Plain bubble sort has no concurrency because each compare depends on the previous swap. Decoupling the compare-swaps into phases is what makes this variant parallel.

The block (parallel) version

  1. Each of p threads owns a contiguous block of n/p elements and qsorts it locally once.
  2. Then p phases. In each phase paired threads do a compare-split: merge the two sorted blocks; the lower rank keeps the smaller half and the higher rank keeps the larger half.
  3. p blocks need at most p phases.
PhaseEven rank's partnerOdd rank's partner
Evenrank + 1rank − 1
Oddrank − 1rank + 1

If the partner is outside 0…p−1, the thread is idle that phase but still calls every barrier; otherwise the count is never reached. With p = 4, even phases pair (0,1) and (2,3); odd phases pair (1,2), and threads 0 and 3 are idle.

Two barriers per phase, because the partner's block is read straight from shared memory:

  • Barrier 1, before any reads: everyone has finished last phase's writes, so reads see consistent data.
  • Barrier 2, after all reads and before any writes: nobody overwrites their block while a slower partner is still reading it.
  • Drop either one and you get a race: merging half-old, half-new data.

Lecture trace (p = 4, n = 16) after the local sorts: t0 15 27 33 36 | t1 35 36 42 43 | t2 12 21 27 49 | t3 6 9 18 40. After 4 phases: 6 9 12 15 | 18 21 27 27 | 33 35 36 36 | 40 42 43 49.

The prof's review questions. Time the local sort (it's part of the algorithm) but not the random initialization. Phases scale with p, each merging O(n/p) data, instead of one O(n) serial merge on one thread. The remaining serial part is mostly barrier waiting and threads idling in odd phases.

5. Thread synchronization

Lecture 5, textbook Ch. 4.4–4.9 and 4.11

Any shared variable that at least one thread writes needs protection. Use the cheapest tool that fits: disjoint writes plus barriers, then a mutex, then a condition variable or semaphore.

Race conditions

A race condition happens when several threads access shared data, at least one writes, and the result depends on timing. x++ is three instructions, so it is not atomic:

load  r, &x     /* T1 loads 5          T2 loads 5           */
inc   r         /* T1 has 6            T2 has 6             */
store r, &x     /* T1 stores 6         T2 stores 6 → one increment lost */

counter1.c: two threads × 1,000,000 increments rarely gives 2,000,000. An atomic operation cannot be interrupted by a context switch. A critical section is code where a race can occur; mutual exclusion means only one thread is inside at a time. Critical sections run serially, so keep them few and short.

Mutex pattern

pthread_mutex_t m;                       /* or = PTHREAD_MUTEX_INITIALIZER */
pthread_mutex_init(&m, NULL);
pthread_mutex_lock(&m);
shared_sum += my_sum;                    /* critical section: keep it tiny */
pthread_mutex_unlock(&m);
pthread_mutex_destroy(&m);

Variants: pthread_mutex_timedlock gives up after a timeout; pthread_rwlock_t allows many readers.

The π example: the classic performance lesson

π = 4(1 − 1/3 + 1/5 − …). Each thread sums a block of terms into a shared sum.

  • No protection: race, wrong answer with two or more threads.
  • Busy-wait inside the loop (every term): threads take turns; 2 threads took 19.5 s vs 2.8 s serial.
  • Sum into a private my_sum and enter the critical section once after the loop: 1.5 s with 2 threads.
  • Up to the core count, busy-wait and mutex versions tie (2.90, 1.45, 0.73, 0.38 s for 1, 2, 4, 8 threads on 8 cores). With 16, 32, 64 threads busy-wait takes 0.50, 0.80, 3.56 s while the mutex stays at 0.38–0.40 s: a spinning thread can hold a core while the thread whose turn it is sits descheduled.

Lesson: enter critical sections as rarely as possible. Do local work privately and combine once.

Producer–consumer and semaphores

A mutex can't express "wait until another thread has done X", because it starts unlocked and only its owner may unlock it. A semaphore can: start it at 0, the producer posts, the consumer waits.

/* thread my_rank sends to dest = (my_rank + 1) % n; all semaphores start at 0 */
messages[dest] = my_msg;
sem_post(&semaphores[dest]);       /* "you have mail" */
sem_wait(&semaphores[my_rank]);    /* wait for mine   */
printf("%s\n", messages[my_rank]);

A binary semaphore initialized to 1 works as a mutex (wait = lock, post = unlock).

Condition variables

The consumer in msgqueue.c spun on getMessage() at 100% CPU even while producers slept (gprof counted 1.27 billion calls). The fix is to sleep on a condition variable:

/* consumer */
pthread_mutex_lock(&m);
while (queue_empty())               /* while, not if: spurious wake-ups, stolen items */
    pthread_cond_wait(&c, &m);      /* unlocks m and sleeps; re-locks before returning */
msg = dequeue();
pthread_mutex_unlock(&m);

/* producer */
pthread_mutex_lock(&m);
enqueue(msg);
pthread_cond_signal(&c);            /* wake one waiter (broadcast wakes all) */
pthread_mutex_unlock(&m);

CPU use drops from about 100% to about 0%. A condition variable doesn't test anything itself; it's a waiting queue.

Read-write locks and the linked list (Ch. 4.9)

Concurrent Member calls are safe; Insert or Delete alongside anything else is not (a reader can follow a pointer into a freed node). Textbook timings, 1000 keys, 100,000 operations:

  • 99.9% Member: rwlock 0.213 / 0.123 / 0.098 / 0.115 s (1/2/4/8 threads) beats one mutex (0.211 / 0.450 / 0.385 / 0.457) and one mutex per node (1.68 / 5.70 / 3.45 / 2.70).
  • 80% Member: rwlock and one mutex nearly tie (about 5 s with 2 or more threads), both slower than 1 thread.
  • One mutex per node is finer-grained but costs two lock calls per node visited plus memory, and was always worst.

Thread safety (Ch. 4.11)

A function is thread-safe if it works correctly when several threads call it at once. Unsafe functions usually hide shared state in static variables: strtok, rand, localtime. Use reentrant versions such as strtok_r with your own save pointer. Incorrect programs can produce correct output: the tokenizer worked on its first run and failed on the second. One correct run proves nothing.

Debugging tools (Lecture 5)

  • gcc -pg, run, then gprof for a function-level profile (it found the busy-wait).
  • nproc --all shows available cores (Docker may get fewer).
  • valgrind --fair-sched=yes ./prog for leaks. Always pass --fair-sched=yes or threaded code may hang.
  • valgrind --tool=drd --fair-sched=yes ./prog for data races (used to grade A1).
  • DRD runs one thread at a time, so counter1.c prints the correct 2,000,000 yet DRD still reports the race.
  • DRD hides leak output, so run leak checks and race checks separately. DRD also flags printf; disable output with #ifdef or use write() while race-testing.
  • Check correctness against a serial version on known inputs; start small and test iteratively.

6. Performance analysis

Lecture 6, textbook Ch. 2.6

Theory (big-O, Amdahl's bound) sets expectations; repeated timed runs plus statistics check them.

Speedup and efficiency

S = T_serial / T_parallel
E = S / p = T_serial / (p × T_parallel)
  • Linear (perfect) speedup: S = p and E = 1. In practice S < p and E < 1 because of overhead and serial parts.
  • Overhead model: T_parallel = T_serial / p + T_overhead. Then E × T_parallel = T_serial / p is the time each core spends on the real problem.
  • Example: T_serial = 24 ms, p = 8, T_parallel = 4 ms → E = 24 / (8 × 4) = 0.75: 3 ms useful and 1 ms overhead per core.
  • Fixed problem size, more threads: E usually falls. Fixed threads, bigger problem: S and E usually rise.
  • Use T_serial from the serial program on one core of the same machine.

Amdahl's law

If a fraction r of the program can't be parallelized and the rest gets perfect speedup:

T_parallel = r × T_serial + (1 − r) × T_serial / p
S(p) = 1 / (r + (1 − r)/p) ≤ 1/r
  • 90% parallel, T_serial = 20 s: T_parallel = 18/p + 2, so S ≤ 20/2 = 10 however many cores you add.
  • r = 1/100 → S ≤ 100 even on thousands of cores.
  • Why not to despair: the serial fraction often shrinks as the problem grows (Gustafson's law), many real programs get huge speedups, and 5–10× may be plenty.

Scalability

A program is scalable if, as p grows, you can grow the problem size at some rate that keeps E constant.

  • Strongly scalable: E stays constant with the problem size fixed.
  • Weakly scalable: E stays constant when the problem size grows at the same rate as p.
  • Example: T_serial = n, T_parallel = n/p + 1 → E = n / (n + p). Multiply both n and p by k: E = kn / (kn + kp) = n / (n + p). Weakly scalable.

Taking timings

  • Time only the part you care about, not I/O or setup. The shell's time measures the whole program.
  • Report wall-clock time, not CPU time; CPU time misses time spent blocked.
  • Pattern: barrier → each thread records its start → work → each records its finish → take the max elapsed.
  • Check the timer's resolution; a millisecond timer can't time a 0.001 s run.
  • The textbook reports the minimum of several runs; the lecture wants the whole distribution analysed. Know both.
  • Run at most one thread per core; more adds scheduling time and variability.

Empirical analysis, the prof's way

  1. Hypothesize: for the sum, run time ∝ n/p + log p, so doubling p roughly halves the time, doubling n roughly doubles it, and speedup stays below p.
  2. Run each (n, p) combination many times (20–25), because run time varies.
  3. Plot the distribution (histograms, box plots) before computing anything.
  4. Compare with a statistical test (paired t-test; p-value < 0.05 means unlikely to be chance). Several t-tests need a Bonferroni correction.

Superlinear speedup, above the line, from an algorithm that can't do that usually means cache effects (smaller per-core working sets fit in cache), user error, too few trials, a timing bug, or scheduler quirks on very short runs.

7. Hardware and caches

Lecture 7, textbook Ch. 2.1–2.2 and 4.10

Memory is far slower than the CPU, so caches and contiguous data decide real performance. ILP is the CPU's own fine-grained parallelism; threads are ours.

The von Neumann model

  • Main memory (addressed locations holding instructions and data), a CPU (control unit decides which instruction runs; the ALU or datapath executes it), registers, and an interconnect (bus). The program counter holds the next instruction's address.
  • von Neumann bottleneck: the CPU–memory interconnect limits how fast instructions and data arrive. CPUs execute over 100× faster than they can fetch from memory, so the CPU starves for data.
  • A process is an executable plus memory (code, stack, heap), file descriptors, security information and state. Threads share most of that and keep their own stack and program counter.

Caches

  • Hit: the data is in cache. Miss: fetch the whole cache line (typically 8–16 times one location, e.g. 64 bytes = 8 doubles), possibly stalling.
  • Levels: L1 (smallest, fastest, per core) → L2 → L3 (largest, slowest, often shared). Check L1 first, then L2, and so on, then memory.
  • Spatial locality: the next access is nearby (z[i+1] after z[i]). Temporal locality: the same location again soon.
  • Write-through updates memory on every write. Write-back marks the line dirty and writes it only when evicted.
  • Mappings (16-line memory, 4-line cache): fully associative = any slot; direct-mapped = slot is line mod 4; n-way set associative = one of n slots in a set. Eviction is usually least recently used.
  • Row-major order: C stores A[i][j] row after row. With i outer and j inner you walk memory contiguously. Textbook: MAX = 4, lines of 4 doubles, a 2-line direct-mapped cache: row order 4 misses, column order 16 (every access). With MAX = 1000 row order ran about 3× faster.

The lecture's rules for cache-friendly data: structs instead of objects, no pointers inside structs, contiguous arrays instead of linked lists, 2D arrays as 1D arrays with index math (a[i*N + j]), and complex objects as several flat 1D buffers (vertex, index and texture buffers in a 3D model). Contiguous data is easy to cache and easy to transfer, which matters for MPI and GPUs.

Virtual memory (Ch. 2.2.4)

Main memory acts as a cache for disk (swap space). Blocks are pages (4–16 KB). An address is a virtual page number plus a byte offset; 4 KB pages use the low 12 bits as the offset because 2¹² = 4096. A page table maps virtual to physical pages; the TLB caches recent translations (16–512 entries). A page that's only on disk causes a page fault. Virtual memory always uses write-back.

Instruction-level parallelism

ILP is done by the CPU and compiler (e.g. -O2), not by you.

Pipeline timing: k stages of 1 ns and n operations take k·n ns unpipelined and k + n − 1 ns pipelined. Textbook: 1000 adds, 7 stages → 7000 ns vs 1006 ns (about 7×).

  • Static multiple issue is scheduled at compile time; dynamic at run time (superscalar).
  • Speculation: guess a branch outcome or that pointers don't alias, execute ahead, and discard the result if wrong. It hides stalls even on single-issue CPUs.
  • ILP fails on dependency chains like f[i] = f[i-1] + f[i-2] (Fibonacci).

Threads and hyper-threading

  • Thread-level parallelism (our threads) is coarser-grained than ILP: whole chunks of code instead of single instructions.
  • Hardware multithreading: fine-grained (switch threads every instruction), coarse-grained (switch only on long stalls), and SMT (several threads share a superscalar core's units at once).
  • Hyper-threading is Intel's SMT: each physical core appears as two. When one thread stalls on memory the other runs. It helps somewhat, but one hyper-threaded core is slower than two physical cores.

Cache coherence and false sharing

  • Cache coherence problem: two cores cache the same variable, one writes it, and the other may keep using its stale copy. Hardware fixes this by snooping (broadcast updates on the bus; other caches invalidate their copy) or with directories (a table of which cores hold each line; scales better).
  • Coherence works on whole cache lines: one write invalidates the entire line in other caches.
  • False sharing: threads write different variables in the same line, so the line bounces between caches. Results stay correct; performance collapses.
  • Textbook matrix-vector multiply (same work, 4 threads): 8,000,000 × 8 had E = 0.707 and 8000 × 8000 had E = 0.750, but 8 × 8,000,000 had E = 0.290 (Table 4.5). There y is just 8 doubles (one cache line) and every thread updates 2 of them millions of times.
  • Fixes: accumulate in a private local variable and write the shared slot once, or pad each thread's data onto its own cache line.

8. Heat diffusion case study

Lecture 8

Each iteration, every interior cell becomes the average of its four neighbours' old values. Threads own bands of rows, and two barriers around one serial step make it race-free without locks.

The model

  • A 2D grid: the outer ring is fixed cold (0), a centred K × K block is fixed hot (the "candle"), and everything else updates.
  • Update rule: next[i][j] = 0.25 * (cur[i-1][j] + cur[i+1][j] + cur[i][j-1] + cur[i][j+1]).
  • Double buffering (ping-pong buffers): read only cur, write only next, swap at the end of each step. Without two grids you'd read neighbours already at step t+1. With them, any traversal order gives bit-identical results, which is what makes this easy to parallelize.
  • Each finished grid is a frame.
  • Stop when max_diff < EPSILON (largest per-cell change, e.g. 10⁻⁴) or the iteration cap is reached. The 16 × 16 toy run converged in 69 iterations; 512 × 512 takes about 2200. It settles into a hot-to-cold gradient, never all cold, because the source stays on.

Foster's steps

  1. Partition: one task per cell. All cells in an iteration are independent; iteration t+1 depends on all of iteration t.
  2. Communication: each cell reads its four neighbours' old values. In shared memory that's just a read.
  3. Agglomerate: a contiguous band of rows per thread, because rows are contiguous in row-major memory. Fixed boundary rows 0 and N−1 aren't assigned to anyone.
  4. Map: ⌊updatableRows/p⌋ rows each, with the first (updatableRows mod p) threads getting one extra. 16 × 16 on 4 threads: 14 rows → rows 1–4, 5–8, 9–11, 12–14. Each thread reads one row above and one below its band.

The per-thread loop

while (1) {
    localMax = 0.0;
    for (i = rowStart; i < rowEnd; i++)
        for (j = 1; j < N-1; j++) {
            if (is_fixed(i,j)) { next[i][j] = cur[i][j]; continue; }
            next[i][j] = 0.25*(cur[i-1][j] + cur[i+1][j] + cur[i][j-1] + cur[i][j+1]);
            localMax = fmax(localMax, fabs(next[i][j] - cur[i][j]));
        }
    thread_max_diff[tid] = localMax;          /* own slot: no lock */
    pthread_barrier_wait(&b1);               /* all of next[] and max_diff[] written */
    if (tid == 0) {                           /* serial section */
        globalMax = max over thread_max_diff[];
        swap(cur, next);
        if (iter % FRAME_STRIDE == 0) writeFrame(cur);
        if (globalMax < EPSILON || iter >= MAX_ITERS-1) converged = 1;
        iter++;
    }
    pthread_barrier_wait(&b2);               /* everyone sees the swap and converged */
    if (converged) break;
}

Why no mutexes: writes are disjoint (each thread writes only its own rows of next and its own thread_max_diff[tid]), and barriers separate the parallel phase from thread 0's serial phase. A single-threaded section must be closed on both sides: barrier 1 so thread 0 reads finished data, barrier 2 so everyone else reads thread 0's results.

Without barrier 2, fast threads start the next iteration before the swap and the converged flag are visible, so they read the wrong grid or miss termination. A misplaced barrier shows up as visible seams at band boundaries in the rendered frames.

The prof's correctness test: run with 1, 4 and 7 threads and diff the frames; they must be identical. This case study returns in the MPI unit, where reading a neighbour's row becomes a halo exchange of messages.

Pitfalls the exam can test

  • Passing &loop_var to pthread_create; forgetting to join (leak); main returning early.
  • Locking inside a hot loop instead of once at the end.
  • if instead of while around pthread_cond_wait.
  • An idle thread skipping a barrier.
  • Busy-waiting with optimization on, or with more threads than cores.
  • False sharing on neighbouring per-thread slots that are written repeatedly.
  • Using the mean on skewed or bimodal timing data; trusting one correct run.
