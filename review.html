Chapter 1

1.1Partition formulas when n isn't divisible by p

Each of p cores runs this loop over its share of n iterations:

my_sum = 0;
for (my_i = my_first_i; my_i < my_last_i; my_i++) {
    my_x = Compute_next_value(...);
    my_sum += my_x;
}

Write formulas for my_first_i and my_last_i so every core gets roughly n/p iterations. Start with the case where p divides n.

Show worked solution

If p divides n, every core gets n/p: my_first_i = my_rank * n/p and my_last_i = my_first_i + n/p (exclusive). Otherwise let q = ⌊n/p⌋ and r = n mod p; the first r cores take one extra.

q = n / p;  r = n % p;
if (my_rank < r) { my_count = q + 1;  my_first_i = my_rank * my_count; }
else             { my_count = q;      my_first_i = my_rank * q + r;   }
my_last_i = my_first_i + my_count;          /* exclusive */

Check with n = 50, p = 8: q = 6 and r = 2, so cores 0–1 get 7 (indices 0–6, 7–13) and cores 2–7 get 6 (14–19 … 44–49). Shares differ by at most 1 and cover every index once.

1.2Partitioning when work per iteration isn't uniform

Same setup as 1.1 (n calls to Compute_next_value split over p cores), but the calls don't cost the same. How would you change the assignment if call i = k takes k + 1 times as long as call 0? What if call 0 takes 2 ms, call 1 takes 4 ms, call 2 takes 6 ms, and so on?

Show worked solution

Both versions have the same shape (the second is just doubled). Equal-sized contiguous blocks are badly unbalanced: the last core gets the most expensive calls. Example with n = 24 and p = 8, three calls each; the total is 300 units, so the ideal is 37.5 per core.

1.7Data vs task parallelism in the tree-structured sum

In the global sum, the first part (each core adds up its own computed values) is data parallelism. In the original second part, the other cores send their partial sums to a master core, which adds them: the master and the others do different jobs, so it's task parallelism. What about the tree-structured second part, where cores pair up in rounds and one of each pair sends while the other receives and adds? Data or task parallelism? Why?

Show worked solution

Both. In each stage every receiving core does the same thing (receive a partial sum, add it) on different data: data parallelism. But in the same stage some cores send while others receive and add: different tasks, so task parallelism. The textbook called the original master-core combine task-parallel for exactly that reason.

1.8Task and data parallelism, and combining them

Faculty members are throwing a party for the students. (a) Identify tasks that different faculty can do at the same time (task parallelism) and work out a schedule. (b) One task is cleaning the house: how can data parallelism split it among the faculty? (c) Combine task and data parallelism to prepare for the party; TAs can pick up the slack.

Show worked solution
  • Task parallelism: give each person a different job — shopping, cooking, cleaning, decorating, music. Schedule around dependencies: shop before cooking, clean before decorating, everything before the guests arrive. Independent jobs run at the same time.
  • Data parallelism for cleaning: split the house by rooms; each person does the same cleaning jobs on their rooms.
  • Combined: a team per job (task parallelism), the cleaning team splits the rooms (data parallelism), and TAs join whichever team has the most left (load balancing).
1.3, 1.5Optional: tree-sum pseudocode, any number of cores

Write pseudocode for the tree-structured global sum (pairs combine in rounds: 0←1, 2←3, …; then 0←2, 4←6, …), assuming p is a power of two. Hints from the textbook: a variable divisor starts at 2 and doubles each round; a core whose rank is divisible by divisor receives and adds, otherwise it sends. A variable core_difference starts at 1 and doubles each round; it gives the partner's rank. Then (1.5) make it work for any p, such as 3, 5, 6 or 7.

Show worked solution 
sum = my_sum;  divisor = 2;  core_difference = 1;
while (core_difference < p) {
    if (my_rank % divisor == 0) {
        partner = my_rank + core_difference;
        if (partner < p) {                /* 1.5: no partner, skip this stage */
            receive value from partner;
            sum += value;
        }
    } else {
        partner = my_rank - core_difference;
        send sum to partner;
        break;                             /* this core is finished */
    }
    divisor *= 2;  core_difference *= 2;
}
/* core 0 holds the global sum */

The partner < p test handles p that isn't a power of two: with p = 6, core 4 has no partner in stage 2 and simply waits for stage 3. Core 0 does ⌈log₂ p⌉ receives. Simulated correct for p = 1–16.

Chapter 2

2.22Foster's method on vector addition

Apply Foster's methodology — partitioning, communication, agglomeration, mapping — to vector addition: z[i] = x[i] + y[i] for i = 0 … n − 1. What are the tasks, the communication between them, the aggregate tasks, and the mapping to threads or processes?

Show worked solution
  1. Partitioning: one task per element, computing x[i] + y[i]. Nothing is inherently serial.
  2. Communication: none between tasks; each needs only its own x[i] and y[i]. In distributed memory, each process is sent its chunk of x and y and z is gathered at the end.
  3. Agglomeration: tasks are identical and independent, so group a contiguous block of about n/p elements into one task.
  4. Mapping: one block per thread or process using the ⌊n/p⌋ + 1 split. Equal work and no communication: embarrassingly parallel.
2.23Two decompositions of the histogram, and which scales better

The histogram problem: count how many of n data values fall into each of bin_count bins. The textbook's design splits the data: each thread finds the bin of every element in its block and counts it in a private loc_bin_counts array; the arrays are then added with a tree-structured sum. Alternative: make each aggregate task all the increments of particular bins. Each thread owns a set of bins and, for every element of data, checks whether it falls in one of its bins. Assuming the data is already distributed and initialized, design a program this way. Which of the two designs is more scalable?

Show worked solution

Each thread owns a range of bins and scans all of data, counting only elements that land in its bins:

/* thread my_rank owns bins my_first_bin .. my_last_bin */
for (i = 0; i < data_count; i++) {
    b = Find_bin(data[i], bin_maxes, bin_count, min_meas);
    if (my_first_bin <= b && b <= my_last_bin)
        bin_counts[b]++;          /* no race: only this thread updates these bins */
}

It needs no locks and no final reduction, but every thread reads all n elements, so each thread's time stays O(n) however many threads you add; only the bin search gets cheaper. In distributed memory every process would also need all the data. The textbook's design (split the data, private loc_bin_counts, tree sum) does O(n/p) work per thread plus O(bin_count · log p) to combine, so the original design scales better.

2.24Shared memory: tree-structured sum, shared vs private variables

In the histogram program each thread ends with its own array of bin counts, loc_bin_cts. Write pseudocode for a tree-structured global sum that adds these arrays — like the global sum of single values, pairs combine in rounds until thread 0 holds the totals. Do the shared-memory version: which variables are shared and which are private?

Show worked solution 
/* shared:  loc_bin_cts[thread_count][bin_count], bin_count, thread_count, barrier */
/* private: my_rank, divisor, diff, partner, b                                     */
divisor = 2;  diff = 1;
while (diff < thread_count) {
    pthread_barrier_wait(&barrier);              /* partner's counts are final */
    if (my_rank % divisor == 0) {
        partner = my_rank + diff;
        if (partner < thread_count)
            for (b = 0; b < bin_count; b++)
                loc_bin_cts[my_rank][b] += loc_bin_cts[partner][b];
    }
    divisor *= 2;  diff *= 2;
}
/* after the threads are joined, row 0 holds bin_counts */
  • Shared: the loc_bin_cts rows (a partner must be able to read them), bin_count, thread_count and the barrier.
  • Private: my_rank, divisor, diff, partner and the loop index b.
  • Nobody "sends" in shared memory: the receiver reads its partner's row directly, and the barrier at the top of each stage takes the place of send and receive.
  • Unlike the distributed version, no thread breaks out of the loop. Every thread must reach every barrier, or the others hang.

Checked against a serial count for 1–16 threads, including non-powers of two; DRD reports 0 errors.

4.4Why mutex performance stops changing beyond the number of cores

Textbook π program: each thread sums its block of terms of π = 4(1 − 1/3 + 1/5 − …) into a private my_sum, then adds it once to the shared sum, protecting that update either with a busy-wait flag or with a mutex. Run times (Table 4.1, 10⁸ terms, 8 cores):

threads    busy-wait    mutex
   1         2.90 s     2.90 s
   2         1.45       1.45
   4         0.73       0.73
   8         0.38       0.38
  16         0.50       0.38
  32         0.80       0.40
  64         3.56       0.38

The mutex version's run time stays roughly constant once there are more threads than cores. What does this suggest about how the threads are scheduled on the processors?

Show worked solution

A thread waiting for a mutex blocks: the OS takes it off the core and runs a thread that can do useful work. So no more threads than there are cores ever run at once, extra threads just wait their turn, and the total work stays the same, so the run time stays at the value set by the core count. Busy-waiting threads keep spinning on cores instead, which is why that version degrades. Table 4.1: the mutex version stays at 0.38–0.40 s from 8 to 64 threads on 8 cores.

4.5Critical section inside vs outside the loop

Move the critical section of the mutex π program inside its for loop (lock, add one term to sum, unlock — every iteration). How does it compare with the book's original busy-wait version, which also had its critical section inside the loop?

/* book's busy-wait version */
for (i = my_first_i; i < my_last_i; i++, factor = -factor) {
    while (flag != my_rank);
    sum += factor / (2*i + 1);
    flag = (flag + 1) % thread_count;
}

The prof suggests reasoning with the Lecture 5 counters instead, where two threads each increment a shared count 1,000,000 times:

/* counter1.c: no lock */
for (i = 0; i < 1000000; i++)
    count++;

/* counter2.c: lock inside the loop */
for (i = 0; i < 1000000; i++) {
    pthread_mutex_lock(&m);
    count++;
    pthread_mutex_unlock(&m);
}
Show worked solution

counter2.c locks around every count++. It's correct, but the critical section runs once per iteration, so the increments are fully serialized, every lock and unlock costs time, and the mutex and count bounce between the cores' caches. Counting into a private local and locking once after the loop is just as correct, with only p critical-section entries.

Against the book's busy-wait-inside-the-loop version: with as many threads as cores the two are close (2 threads, 2 × 2,000,000 increments: busy-wait 0.32 s, mutex 0.28 s). With more threads than cores busy-waiting collapses — 4 threads on 2 cores took over 2 minutes busy-waiting against 0.63 s with the mutex — because the strict turn order makes threads spin while the thread whose turn it is sits descheduled.

4.7Creating threads until it fails, and what detaching changes

Change the Pthreads hello program so main creates threads in an infinite loop and never joins them:

void* Hello(void* rank) {
    printf("Hello from thread %ld\n", (long) rank);
    return NULL;
}
/* in main */
pthread_t handle;
for (long thread = 0; ; thread++)
    pthread_create(&handle, NULL, Hello, (void*) thread);

The "Hello from thread" messages eventually stop, though the program keeps running. Why? (Check what pthread_create returns.) Then call pthread_detach(handle) after each create: what changes?

Show worked solution

The messages stop because pthread_create starts returning an error: EAGAIN, "Resource temporarily unavailable". The threads are joinable and never joined, so each finished thread keeps its resources (stack, thread record) until somebody joins it, and the system runs out. A detached thread frees its resources as soon as it finishes, so creation keeps succeeding; only the number alive at the same moment is limited.

On the test machine the joinable version failed after 32,753 threads; the detached version created 200,000 with no failure and was stopped there.

4.8Producer–consumer with a mutex and a flag

Producer–consumer with a mutex instead of semaphores. The two threads share a mutex and a flag message_available, initialized to false, and each runs:

while (1) {
    pthread_mutex_lock(&mutex);
    if (my_rank == consumer) {
        if (message_available) {
            print message;
            pthread_mutex_unlock(&mutex);
            break;
        }
    } else {                       /* my_rank == producer */
        create message;
        message_available = 1;
        pthread_mutex_unlock(&mutex);
        break;
    }
    pthread_mutex_unlock(&mutex);
}

Write this for two threads. Generalize it to 2k threads (odd ranks consume, even ranks produce), then so every thread is both: thread q sends to (q + 1) mod t and receives from (q − 1 + t) mod t. Does it use busy-waiting?

Show worked solution

With two threads the consumer loops lock, check the flag, unlock, until the producer sets it. For the ring, give each thread its own message slot, flag and mutex:

/* shared: msg[t], available[t] (all 0), m[t]; dest = (my_rank + 1) % t */
pthread_mutex_lock(&m[dest]);                     /* produce */
msg[dest] = my_msg;  available[dest] = 1;
pthread_mutex_unlock(&m[dest]);

while (1) {                                        /* consume */
    pthread_mutex_lock(&m[my_rank]);
    if (available[my_rank]) {
        printf("%s\n", msg[my_rank]);
        pthread_mutex_unlock(&m[my_rank]);
        break;
    }
    pthread_mutex_unlock(&m[my_rank]);
}

For 2k threads with even producers and odd consumers, pair thread 2j with thread 2j + 1 and give each pair one slot. Yes, it busy-waits: the consumer keeps locking, checking and unlocking until the flag is set. In a 5-thread run one thread checked its empty flag 200,026 times before its message arrived. A semaphore or condition variable would let it sleep instead.

4.9Deadlock with two mutexes

A program has two shared data structures, each protected by its own mutex (mut0 and mut1); a structure may be accessed only while holding its mutex. Two threads do this:

time   thread 0                      thread 1
 0     pthread_mutex_lock(&mut0);    pthread_mutex_lock(&mut1);
 1     pthread_mutex_lock(&mut1);    pthread_mutex_lock(&mut0);

(a) What happens? (b) Would it still be a problem with busy-waiting on two flag variables instead of mutexes? (c) With semaphores instead of mutexes?

Show worked solution
  • (a) Each thread holds one mutex and asks for the one the other holds, so both block forever: deadlock. Run as written, the program was still stuck after 3 s.
  • (b) Busy-waiting with two flags: still a problem. Each thread spins forever on a flag the other will never clear, and burns a core doing it.
  • (c) Semaphores: still a problem. Each sem_wait blocks forever.
  • Fix in every case: acquire the locks in the same global order (e.g. always mut0 before mut1).

4.13Read lock for the search phase, write lock for the update phase

Insert and Delete on a shared linked list have two phases: first a search for the position, which only reads the list, then (if needed) the insertion or deletion, which writes it. Programs often split these into two function calls. Would it be safe to hold a read lock for the first phase, then a write lock for the second? Explain.

Show worked solution

No. Between releasing the read lock and getting the write lock, another thread can change the list: it can delete the pred or curr node you found (you then link into freed memory) or insert the same key (you then insert a duplicate). The position found in phase 1 can be stale by phase 2. Pthreads read-write locks can't be upgraded atomically either; asking for the write lock while still holding the read lock may deadlock or return an error. Hold the write lock for the whole Insert or Delete, or re-check the position after taking it.

4.17False sharing between non-adjacent threads

Matrix-vector multiply, run with m = n = 8000 and 4 threads (so each thread computes 2000 consecutive elements of y):

/* Program 4.13: y = A*x, A is m x n; m, n, A, x, y are shared */
void* Pth_mat_vect(void* rank) {
    long my_rank = (long) rank;
    int local_m = m / thread_count;
    int my_first_row = my_rank * local_m;
    int my_last_row  = (my_rank + 1) * local_m - 1;
    for (int i = my_first_row; i <= my_last_row; i++) {
        y[i] = 0.0;
        for (int j = 0; j < n; j++)
            y[i] += A[i][j] * x[j];
    }
    return NULL;
}

A cache line holds 64 bytes, or 8 doubles. If threads 0 and 2 run on different processors, can false sharing between them occur for any part of y? Why? What about threads 0 and 3?

Show worked solution

Thread 0 computes y[0..1999], thread 1 y[2000..3999], thread 2 y[4000..5999] and thread 3 y[6000..7999]. A line holds 8 consecutive doubles. Thread 0's last element, y[1999], is 2001 elements from thread 2's first, y[4000] (and 4001 from thread 3's), so no line can hold elements of both. False sharing between 0 and 2, or 0 and 3, is impossible, whichever processors they're on. It can only happen at the boundary between adjacent threads (0–1, 1–2, 2–3), and even there it's unlikely: one thread touches the boundary at the end of its loop and the other at the start.

4.19Parts a and b: padding vs thread-private storage

In that 8 × 8,000,000 run, each thread updates its two elements of y 8,000,000 times, and all of y can sit in one cache line, so the line keeps bouncing between processors (false sharing). Fix it two ways: (a) pad y so that, even with the threads running in lock-step, no cache line holding an element of y is shared by two threads — with 8 doubles per line and 4 threads, allocating at least 48 doubles is enough; (b) give each thread private storage for its part of y during the loop and copy it into the shared y when it's done. How do the two compare?

Show Program 4.13
/* Program 4.13: y = A*x, A is m x n; m, n, A, x, y are shared */
void* Pth_mat_vect(void* rank) {
    long my_rank = (long) rank;
    int local_m = m / thread_count;
    int my_first_row = my_rank * local_m;
    int my_last_row  = (my_rank + 1) * local_m - 1;
    for (int i = my_first_row; i <= my_last_row; i++) {
        y[i] = 0.0;
        for (int j = 0; j < n; j++)
            y[i] += A[i][j] * x[j];
    }
    return NULL;
}
Show worked solution
  • (a) Padding: spread y so no cache line ever holds elements of two threads, whatever the alignment. With 4 threads and 8 doubles per line, allocate 48 doubles and let thread t use y[8 + 10t] and y[9 + 10t]: neighbouring threads' elements are 9 apart and the ends are padded, which was checked for all 8 alignments. It costs memory and makes indexing awkward.
  • (b) Thread-private storage: each thread accumulates its rows in a local array on its own stack, then copies the results into the shared y once at the end. The shared line is written a handful of times instead of 16,000,000, with no padding or alignment assumptions.

Both should bring the 8 × 8,000,000 efficiency (0.290 with 4 threads in Table 4.5) up toward the other inputs'; (b) is simpler and at least as fast.
